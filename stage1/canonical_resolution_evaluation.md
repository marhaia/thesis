# Canonical Analysis Resolution — Candidate Evaluation

This note records the evidence behind the canonical analysis resolution used by
the Stage-1 visual-feature extractor (`CANONICAL_LONG_SIDE` in
`stage1/visual_complexity.py`). It exists so the choice is reproducible and
auditable; it is not runtime code.

The numbers below are regenerated by the committed, path-agnostic CLI script
`stage1/tools/canonical_scale_eval.py`, which writes its artifacts to
`stage1/canonical_eval/` (candidate comparison CSV/JSON, held-out sample
manifest and results, and the per-fixture scale report). This selection was an
**exploratory, evidence-based comparison**, not a pre-registered experiment: the
candidates, sample and tolerances were examined together, so the conclusions are
reported as an engineering decision rather than a confirmatory result.

## Why a canonical resolution exists

Several of the eight visual features use fixed pixel-scale operators (Canny at a
fixed sigma, fixed-scale Gaussian / steerable pyramids, area-normalised element
counting). On the raw screenshot these operators make the feature values depend
on the native pixel resolution: the **same layout** rendered at 1x / 2x / 3x
produced materially different feature vectors, which made the downstream
headline score resolution-dependent (deterministic, not flaky). The diagnosis
attributed essentially the entire headline gap to `feature_congestion`
(amplified by the `content_presence` max gate), with `edge_density` and
`interactive_element_density` also inherently pixel-scale dependent. These three
are the **pixel-scale drivers**. They are a subset of the five Stage-1 features
that feed the HCEye-derived index (`HCEYE_FEATURE_MAP` maps `edge_density`,
`feature_congestion`, `interactive_element_density`, `layout_symmetry` and
`visual_hierarchy`): `layout_symmetry` and `visual_hierarchy` also affect the
index and are reported in full below — they are not treated as non-score-driving.

The fix computes all eight features on a fixed, aspect-ratio-preserving
canonical resolution (resize so the long side equals `CANONICAL_LONG_SIDE`),
applied once before feature extraction. A later, separate change extended the
same canonical analysis image to the two remaining score-driving,
element-derived inputs — `whitespace_ratio` and the OCR-derived `text_density` —
so every value that feeds the layout `experimental_complexity_index` now shares
one analysis scale (see `stage1/canonical_layout.py`). The original image and
its native coordinate system are deliberately kept for the interaction path:
element detection for bounding boxes, overlays, target selection, native
contrast diagnostics and the Jokinen search model still run natively.

## Candidate comparison

Evaluated on three deterministic synthetic layouts (hard-edged UI, text/line
UI, gradient/low-detail UI) rendered at 1x/2x/3x, plus a deterministic UEyes
*selection* sample (first + middle image of each sorted **authorized** category
`desktop` / `mobile` / `web`; `poster` is excluded, so the selection is six
images and contains zero posters). The selection sample IDs are recorded in
`stage1/canonical_eval/candidate_comparison.json`.

> Sample scope: the corpus-wide native-resolution statistics above use the full
> 1,485-image authorized UEyes corpus (poster excluded), but this candidate
> feature comparison does NOT. The scale-gap objective uses the three synthetic
> fixtures, and the perturbation tie-breaker uses only the six declared
> authorized selection images. No candidate feature-perturbation number is
> computed over all 1,485 images.

**Primary objective — scale gap of the pixel-scale drivers**
(`feature_congestion`, `edge_density`, `interactive_element_density`), worst-case
relative 1x/2x/3x gap after canonicalisation, measured on the *re-rendered*
synthetic fixtures (regenerated numbers in
`stage1/canonical_eval/candidate_comparison.csv`):

| candidate | mean | worst |
|-----------|------|-------|
| 1024 | 0.72 % | 4.43 % |
| 1280 | 0.73 % | 4.38 % |
| 1440 | 1.32 % | 6.66 % |

1024 and 1280 are tied (< 5 %); 1440 is clearly worse because the larger upscale
of small inputs re-introduces interpolation artefacts.

> Methodology note: the scale objective is measured ONLY on the re-rendered
> synthetic fixtures. Re-rendering a layout natively at 1x/2x/3x is the faithful
> model of "the same UI captured at a different resolution/DPI". Raster-upscaling
> a single stored screenshot is *not* — it is a lossy round-trip and it also
> biases the ranking toward candidates far below the native size (the 1x no-op
> disappears once the candidate < native). Real screenshots are therefore used
> for the perturbation tie-breaker below, not for the scale objective.

**Tie-breaker — feature perturbation and cost.** For the UEyes *selection*
images (six authorized GUI images: first + middle of each sorted `desktop` /
`mobile` / `web` category — `poster` is excluded), the eight features at each
image's native size are compared against the features after **one direct
native-to-candidate resampling** to the candidate long side. This is a single
resampling per image and does **not** build artificial 2x/3x screenshot
variants; note that canonicalisation *does* upscale originals whose native long
side is below the candidate (a real resampling that perturbs features), so this
is not a "no upscaling" measurement. The mean / worst relative feature change is
(`stage1/canonical_eval/candidate_comparison.csv`):

| candidate | mean perturbation | worst perturbation |
|-----------|-------------------|--------------------|
| 1024 | 9.57 % | 111.42 % |
| 1280 | 6.41 % | 76.92 % |
| 1440 | 10.33 % | 73.62 % |

On the authorized selection images 1280 has the **lowest mean** real-image
perturbation (6.41 %). It does **not** have the lowest worst-case perturbation:
1440 has the lowest **worst** perturbation (73.62 %), narrowly below 1280
(76.92 %). 1280 is selected because it ties for the best primary scale-gap
objective *and* has the lowest mean perturbation, whereas 1440 loses the primary
objective (and costs more); 1024 downscales the majority (~70 %) of the corpus
and has the highest mean perturbation.

- 1024 downscales ~70 % of the corpus and perturbs features most on real images
  (mean 9.57 %).
- 1280 downscales only ~30 % of the corpus and perturbs features least on the
  mean (6.41 %; ~0 % for the many native-1280 web images).
- 1440 has the lowest corrected **worst** perturbation but loses the primary
  scale-gap objective and adds compute cost over 1280.

> Runtime note: measured extraction cost per image is an **environment-specific
> observed measurement**, not a universal benchmark. The evaluation tool records
> the Python / NumPy / OpenCV versions, platform and per-phase elapsed time in
> `stage1/canonical_eval/run_environment.json`; historical fixed "≈ N s/image"
> claims that could not be reproduced from executable output have been removed.

## Decision rule and selection

Select the smallest candidate that (a) minimises the pixel-scale-driver scale
gap **and** (b) does not force the majority of the corpus to be downscaled.

- 1024 fails (b): it downscales 70 % of the corpus and has the highest mean
  feature perturbation on real images.
- 1440 fails (a): worse scale gap, plus higher cost. It does have the lowest
  corrected **worst** perturbation, but that does not rescue the primary
  scale-gap objective.
- **1280 satisfies both** — tied for the best scale gap, lowest **mean**
  real-image perturbation, downscales only 30 %, and sits just above the corpus
  median long side (1188 px). **Selected.**

This is an exploratory, evidence-based selection, not a default and not a
pre-registered confirmatory test: 1024 tied 1280 on the primary objective and
lost only on feature perturbation, and 1440's lower worst-case perturbation does
not overturn its loss on the primary scale-gap objective.

## Held-out real-UI scale evaluation

A deterministic UEyes sample (seed 20240607, two images per **authorized**
category, **excluding** the six authorized images used to select 1280) is
evaluated by `stage1/tools/canonical_scale_eval.py`. `poster` is excluded, so
the held-out sample is six images and contains zero posters. Sample IDs,
category and seed are in `stage1/canonical_eval/heldout_ueyes_manifest.csv`; the
full per-image numbers (eight raw features, the canonical and the baseline
native `whitespace_ratio`, canonical element count and per-scale normalised
canonical bounding boxes, plus analysis provenance) are in
`stage1/canonical_eval/heldout_ueyes_results.json`. The UEyes images themselves
are not added to git.

**Normalized held-out scores are withheld (pending canonical norms).** The only
available `feature_norms.json` was built at NATIVE resolution, so
percentile-normalising these CANONICAL-domain features against it would be a
domain mismatch. The interim held-out artifact therefore contains **raw visual
features, canonical layout measurements and provenance only**. The
percentile-normalised HCEye inputs and any derived HCEye/layout index are
emitted as an explicit machine-readable `unavailable` marker
(`normalized_scores_status`, reason
`domain_mismatch_native_norms_vs_canonical_features`) — never as a neutral
constant or fallback value. Valid normalized held-out scores remain **pending
the separately authorized canonical visual-feature norm generation**.

Important honesty caveat about the method: a real screenshot exists at a single
native capture only, so the 2x/3x variants here are produced by **raster
enlargement** (`cv2.resize`) — one direct resampling, not a native re-render at
a higher resolution, and not an artificial 2x/3x screenshot pipeline. These
results are therefore reported **descriptively** — the prospective ≤ 1.0-point
synthetic acceptance guard is **not** applied to them, and any remaining
differences are **not** assumed to disappear under a true native re-render.

What the evaluation shows:

- **The score-driving layout path is now canonical.** `whitespace_ratio` and
  `text_density` are measured on the canonical analysis image via the production
  helper `measure_canonical_layout`. The report gives, per image, the canonical
  and the baseline native `whitespace_ratio` absolute gaps across scales; on the
  canonical path the whitespace gap collapses relative to the native baseline
  (e.g. web image `1408dc`: native whitespace gap ≈ 0.217 vs canonical ≈ 0.001).
- **The baseline (pre-fix) native-whitespace measurement is retained for
  comparison only.** Running whitespace on the native raster reproduces the
  previously observed strong scale sensitivity. It is kept purely to
  reproduce/explain the baseline, not because it still feeds any score. (Because
  the derived index is now withheld as a domain mismatch, the index-level
  decomposition is no longer reported; only the raw whitespace gaps are.)
- **Canonical element geometry is stable.** Per-scale normalised canonical
  bounding boxes are saved, and the 1x set is matched against the 2x and 3x sets
  (greedy best-IoU one-to-one, IoU ≥ 0.5). To avoid hiding extra detections, the
  report gives the **directional 1x-reference coverage**, the **candidate-side
  coverage** and a **symmetric coverage** (`2·matched / (n_ref + n_cand)`); IoU
  values are clamped to [0, 1]. Images whose 1x reference detects **zero** boxes
  are marked **not applicable** rather than reported as coverage/IoU = 0. Across
  the six authorized held-out images the mean matched IoU is ~0.98–1.00,
  reference coverage 0.91–1.00 and candidate coverage 0.75–1.00 (the candidate
  figure exposes a few extra enlarged-image detections that a reference-only
  coverage of 1.0 would mask).
- **A raster-stress residual remains on the canonical path.** Even with
  whitespace canonicalised, canonical measurements are not perfectly invariant
  on raster-enlarged real images (small canonical whitespace gaps and element
  count ranges persist). Because this is a raster-enlargement artefact rather
  than a native re-render, it is reported as an observed residual and is **not**
  assumed to vanish under true native re-rendering.

The native detection path (bounding boxes, overlays, target selection, contrast
and the Jokinen search model) is kept native **by design** for coordinate
accuracy. It no longer feeds the layout score, so its native-scale behaviour is
a deliberate architectural choice rather than an unresolved defect of the score.

Scope of the scale evidence: only the reduced HCEye rule index (visual features
+ whitespace, no saliency, no OCR, no modifiers) is exercised across scales. The
**complete production `layout.experimental_complexity_index` with the real
UMSI++ saliency model and real EasyOCR text density has NOT been
scale-validated** and no such claim is made here.

## Scope / limitations

- Applies to general/source-domain GUI analysis only. Automotive transfer and
  UIED/Rico remain out of scope; Driver Glance stays disabled / Future Work.
- The current `feature_norms.json` was built at native resolution. It is **not**
  modified by this change. Because canonicalisation makes the 1x/2x/3x raw
  vectors materially equal, the headline scale-invariance test passes under the
  existing norms; a full norm rebuild at the canonical resolution is a separate,
  later step and is intentionally **not** performed here.
- **Normalized held-out scores remain pending the separately authorized
  canonical-norm generation.** Because the stored norms are native-domain,
  percentile-normalised held-out values and any derived HCEye/layout index are
  withheld (see `normalized_scores_status`) rather than presented against
  incompatible norms. A dedicated, visual-only generator
  (`stage1/tools/canonical_visual_norms.py`) is provided to produce the future
  canonical `canonical_visual_feature_norms.json`; it refuses to touch
  `feature_norms.json` / `sensitivity_lookup.json`, and the full 1,485-image
  generation is a separately authorized run, not performed here.
